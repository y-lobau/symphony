# Plyn Symphony test cases

| Case | Expected result | Verification |
| --- | --- | --- |
| Valid app installation | GitHub issue reads and `github_api` calls use an installation token from the configured command. | `github_adapter_test.exs`: token command |
| Expired token | A later GitHub request obtains a refreshed token without restarting Symphony. | `github_adapter_test.exs`: token command re-evaluation; `test_github_app_auth.py`: cache expiry |
| Missing or failed app credential | GitHub work fails explicitly and never uses a personal token from the environment. | `github_adapter_test.exs`: failed token command; `test_github_app_auth.py`: failure |
| Git repository push authentication | The helper answers only for the configured HTTPS GitHub repository and returns an app token. | `test_github_app_auth.py`: credential request scope |
| Commit creation | The unattended worker can write Git metadata, create a branch and commit, and attribute the commit to the app bot rather than the Mac owner. | `test_github_app_git.py`: workspace Git configuration; manual Codex sandbox commit probe and GitHub attribution check |
| Ready issue dispatch | An open issue with `ready-for-agent` in Plyn Release **Ready** or **Backlog** is eligible; any other Project Status or missing label is not. | Inspect issue labels and Project Status against the live queue. |
| Dispatch completion | After opening a pull request, the worker moves the issue to **In review** and leaves `ready-for-agent` in place; polling does not start another run. | Inspect the issue Project Status and label after a completed run. |
| Agent start tracking | Starting an eligible issue assigns it to `y-lobau` and changes its Plyn Release Project Status to `In progress`. | Inspect the issue assignee and Project Status after dispatch. |
| Human input handoff | A Codex input-required event blocks the run and changes Plyn Release Project Status to `Human in the Loop`, retaining `ready-for-agent`. | Simulate an app-server input-required event and inspect the issue's Project Status and labels. |
| Human input resume | A blocked issue is eligible for a fresh run after a human reply is added as an issue comment and Project Status changes to **Ready** or **Backlog**; the new run reads recent comments and sets **In progress**. | Reply to a blocked issue, move its Project Status, and inspect the next run. |
| Project status read failure | If GitHub cannot confirm the issue's Project Status, Symphony does not dispatch it. | Simulate a failed Projects query and inspect the candidate queue. |
| Issue history lifecycle | A new run and its turns appear under the issue; retries and human resumption create further runs under that issue, and records survive a service restart. An open run at restart becomes interrupted. | `history_test.exs`: run, restart, and recovery cases |
| History metrics | Run and issue totals include input/output/total tokens, cached input as a subset of input, derived non-cached input, active duration including an open run's elapsed time, completed Codex messages, completed context compactions, and one count per human-input stop. Missing cache or compaction data stays unknown, including in mixed old/new issue totals. Reasoning, streaming deltas, tool calls, and GitHub comments do not count as messages; token volume does not imply a compaction. | `history_test.exs`: event accounting, cache usage, compaction events, legacy records, and aggregation |
| History context, latest output, and stop | A run records the workflow revision, effective model and reasoning effort, outcome, and an uncategorized human-input stop signal/reason when present. It retains only the latest completed agent-authored output excerpt (one line, at most 500 characters) and its timestamp; streaming fragments, reasoning, tool output, and protocol notifications cannot replace it. The excerpt survives restart, and older runs without one show unavailable. | `history_test.exs`: context, last-output, restart, and stop cases |
| Historical events and pull requests | Stored structural events retain observable milestones, completed context compactions, retries, errors, stops, status changes, and successful PR creation with a deduplicated link on the issue tracker host; a worker that fails before its first turn still records a safe, useful failure cause. The issue page does not show the event log. No full message or tool payload is stored. | `history_test.exs`: event, compaction, startup failure, and PR cases |
| History dashboard and API | The local-network dashboard pages issue summaries so older issues remain reachable and opens an issue detail page with processed-token totals, a visible cached/non-cached input split or unknown state, a context-compaction count or unknown state, and ordered run cards showing the latest Codex output excerpt. The event log is omitted from the page. A connected page updates after a completed agent message. The JSON API pages summaries and returns the same run metrics and excerpt without a transcript. | `history_web_test.exs`: API, LiveView, and live-update cases |
| Historical status | A current running/retrying/blocked state overrides last observed tracker status; a failed tracker refresh keeps the dated previous observation. | `history_test.exs` and `history_web_test.exs`: status cases |
